# plinth

plinth is a Rust CLI that adds the tooling around a project and sets up its GitHub repo in the house
style `~/Projects/tide` established: mise + just, `just ci` as the gate, squash-only PRs behind a
`main` ruleset, a Conventional Commit title check, release-please, monthly grouped Renovate
updates, PR and issue templates, and a pre-commit guard. The project itself comes from its own tool
first (`cargo new`, `npm create astro`, `bun create vite`); `plinth init` then works out the
language from its manifest. This repo is set up exactly the way plinth sets up others.

plinth sets up Rust projects and TypeScript ones (with npm, pnpm or bun) so far. A TypeScript
package is one of a few kinds, read from its dependencies: an Astro site, a React app built with
Vite, a Hono server, or a plain package. Each kind adds its own checks, lint rules and build to one
TypeScript gate. A workspace of several packages gets one gate at its root that covers each
package by its kind. The TypeScript the project asks for picks the linter: on 7, type-aware oxlint,
as typescript-eslint can't run on 7's Go compiler; on 6, or with no version asked for, ESLint with
typescript-eslint. Astro stays on 6 for `astro check`, and a workspace runs one TypeScript. Anything
else is refused with a message saying so. Python (uv) is next.

## Principles

- **Never prompts.** Every choice is a flag, so Claude or any other harness can drive it. What can be
  read from the project, such as its language, is read rather than asked.
- **Never touches the project's code.** plinth adds files the project lacks, appends missing lines
  to `.gitignore` and `.gitattributes` and its house rules to an AGENTS.md of the project's own,
  and leaves every other existing file as it is. A JavaScript project's gate tools go in as dev
  dependencies through its own package manager. No framework or source templates. The one
  exception is a monorepo whose packages were made by their own tools and have no root yet: plinth
  assembles the root, which means writing the root `package.json` (or `pnpm-workspace.yaml`), giving
  a nameless package a `name`, moving a package's pnpm settings to the root, and removing the
  packages' own lockfiles and `node_modules` for one install at the root. The dry run lists each.
- **Owns the gate, not the project's config.** The gate's recipes are in `plinth.just` and a
  TypeScript project's lint rules in `plinth.eslint.mjs`, or `plinth.oxlintrc.json` on TypeScript 7;
  each starts with a `Generated by plinth` line, and plinth rewrites it on every run while that line
  is there, so the gate keeps up with the packages a monorepo gains. The `justfile` and
  `eslint.config.mjs` or `.oxlintrc.json` that import them are the project's, written once, and
  their recipes and rules win. Without the first line, or without a file importing it, an owned file
  is the project's too. `.prettierrc.json` stays the project's; plinth says what a new package needs
  added to it.
- **Practise what it preaches.** The shared files plinth generates match this repo's own copies; a
  test enforces it. Change one, change both. The TypeScript layers, which this repo can't run, are
  held to the same bar by end-to-end tests: each kind's own creator (create-astro with each package
  manager, create-vite, create-hono, `bun init`, and monorepos of them with each package manager),
  plinth, then the project's own `just ci`. Renovate
  scans `templates/` too, so its PRs bump an action or a mise tool in both copies at once.
- **Asks before touching GitHub.** `--dry-run` shows the `gh` calls; new repos are private unless
  `--public` is given.

## Layout

```
src/main.rs        CLI: `init` (clap), name checks, the dry-run report
src/lang.rs        works out the language, package manager and kind of package; the setup commands
src/workspace.rs   finds a monorepo's packages from its globs, or assembles a root for them
src/scaffold.rs    renders the layers, sorts them into add / append / update / leave alone, writes them
src/github.rs      the first commit, `gh repo create`, repo settings, labels, the `main` ruleset
src/step.rs        a command as data, so `--dry-run` prints exactly what a run would do
templates/base/    files every project gets; `.j2` files are rendered with minijinja
templates/rust/    the Rust layer; a file here replaces a base file at the same path
templates/typescript/  the TypeScript layer, rendered per kind, with npm's mise.toml;
                   typescript-pnpm/ and typescript-bun/ replace that
tests/init.rs      runs the binary, including the checks that it reproduces this repo
.claude/           settings.json: Claude Code may run `just` unprompted and can't read `.env` files
.claude-plugin/    marketplace.json: this repo is a Claude Code marketplace with one plugin
plugin/            the plinth plugin: plugin.json and skills/plinth/SKILL.md, which drives the CLI
```

## Git and GitHub

- Changes reach `main` only through a pull request whose `check` passes; a ruleset enforces it.
  One branch per change, kept to one commit. Branches needn't be up to date with `main`; use
  "Update branch" when a PR should be re-tested against it first.
- PRs are squash-merged, so the PR title becomes the commit on `main`. Titles are Conventional
  Commits, `type: description`, with the description in the imperative and starting lowercase.
  `feat` releases a minor version, `fix` and `perf` a patch, and `!` after the type a major;
  `refactor`, `docs`, `test`, `build`, `ci`, `chore` and `revert` don't release.
- release-please owns `CHANGELOG.md` and the version, and Renovate owns dependency and tool
  updates; don't edit those by hand. release-please's PRs need "Approve workflows to run" clicked
  once before their `check` runs (see `.github/workflows/release.yml`).
- Labels: `feature`, `bug`, `docs`, `ci`, `dependencies`.
- Wait for Murad before merging.

## Releases

release-please makes each release from the merged titles. `release.yml` then starts
`publish.yml` on the new tag, which builds `x86_64-unknown-linux-gnu` and `aarch64-apple-darwin`,
attests each `plinth-<target>.tar.gz` (`actions/attest`; attestations need a public repo or
Enterprise Cloud) and attaches them, the files `mise use -g github:muradmadi/plinth` installs.
The `publish.yml` hook in `release.yml` is shared with every generated project; only plinth has a
`publish.yml` so far.

## Toolchain

Rust, just and the audit tools are pinned in `mise.toml`; run `mise install`, then `just setup` once.
`just check` is the gate: `cargo fmt --check`, clippy with warnings as errors, `cargo test` with
the slow end-to-end tests (they create projects with cargo, create-astro, create-vite, create-hono
and `bun init`, so they need the network), then `just audit` (typos, actionlint, zizmor, shellcheck on the hook, gitleaks over every commit). A zizmor
finding is fixed, or ignored inline with `# zizmor: ignore[<audit>]` and the reason. Murad is new to
Rust (background in C# and C++), so explain Rust-specific choices briefly in PRs where they aren't
obvious.
